O projeto normalmente está contido dentro da pasta src, dividido entre model e service, e ambos não acessáveis
  - Neste caso, é um projeto mais simples, então não temos o src
  - O model é quem interage com o banco de dados
  - O service é onde está a regra de negócio

Nos testes, precisamos de um alvo (a feature) e precisamos mockar é qualquer coisa que não está no alvo (exemplo: acesso ao banco de dados)

As chamadas feitas pela a API não acessam a camada de model, a API chamará o service, que chamará o model

REST é um estilo de arquitetura de API, um jeito com o qual API são criadas
  - API é a interface que se comunica com seu código
  - É preciso ter um servidor rodando, geralmente via HTTP (podemos usar postman)
  - No caso do js, o rest tem que ter o app.js, pois é onde ele vai levantar o servidor
    - Nesse arquivo app.js, a gente tem nossas rotas (endpoint)

Na prática:
  REST - Alguém chama o http
  REST - Ele chama um endpoint
  REST - O endpoint chamará o tipo de request (get/post/put/delete)
  APLICAÇÃO - O request chamará o método da camada de service para realizar a operação
  APLICAÇÃO - O método service chamará o método na camada de model, que irá se conectar com o db para coletar os dados usados para a operação

No arquivo de rotas, é possível saber se o enpoint precisa ou não estar logado, através da validação do token
  - Essa validação é feita na camada de controller

Caso algum parâmetro da requisição esteja errado, cabe a camada de service informar para as camadas superiores do erro

A arquitetura criada pelo copilot tem os seguintes erros estruturais

SuperTest é uma lib usada para testes de API, e ela permite que se faça requisições, extraia informações e valide os dados
  - SuperTest é o postman por linha de comando
  - É preciso instalar o mocha para teste de unidade e chai para as asserções
  - Também instalaremos o sinon, que nos ajudará a mockar as informações externas ao controller, nesse caso, será mockado a camada de serviço, usado para testes de componente

Se no teste da requisição houver um retorno 500, significa que o dev não tratou o erro (utilizando o bloco de try/catch)
  - Quando fizer os testes do projeto final, reescrever o código (se necessário)
  - Analisar o código é bom para garantir um código mais seguro

O app.js é nossa api, e a diferença é que o teste do controller olha para dentro do projeto, enquanto o teste da api procura ele na web
  - O nosso app é o que está expondo a api
  - O nosso server é o servidor web que está expondo a api via http

Para fazer teste real no servidor com rest, o request não será feito para o app (no caso, request(app))
  - Para isso, a gente sobe o servidor real, se não, não funcionará
  - Porém, há uma demora maior (mas ainda sim mínima) do que testar localmente ou com mock
  - Mesmo com a demora, é necessário esse tipo de teste para garantir a comunicação real entre as partes
  - Nesse caso, a diferença entre testar diretamente o controlador e o servidor real é a porta onde o servidor ta hospedado, podemos validar se o servidor está no ar corretamente
    - As vezes, pode haver erro de compatibilidade entre a máquina onde está o servidor com libs usadas no projeto
  - No método de request, ao invés do app, chamaremos o endereço http (request('http://localhost:3000'))
    - Antes de rodar os testes externos, é preciso colocar o servidor no ar primeiro

Para validar as respostas vinda do servidor, eu faço comparação com o arquivo de respostas que fica em fixutres
  - Pra isso, a gente prepara os dados e carrega o arquivo, ignorando os campos dinâmicos
  - A gente compara o body da resposta com os dados do arquivo carregado
  - É preciso ter um fixture para cada resposta
  - Uma boa prática não alterar o campo dinâmico para fazer o teste passar, e sim remover com delete
    - Mas é possível sim atualizar o valor dinâmico dentro do fixture para validação do teste
  - Há um plugin pro javascript chamado chai exclude que exclui os valores que não quero
